Supervisor authorization for one authority launch
Status: missing-feature baseline reproduced on both hosts. Production authorization remains unimplemented.

Invariant

Only the registered supervisor can authorize activation for one exact owned launch and service connection.
An authorization cannot survive a later generation, a supervisor key change, or an issuer restart.

Trust and production integration

The supervisor must retain launch ownership before signing.
Use the launch_id from the retained process scope and matching native scope.
The supervisor obtains the service authentication result through that owned launch's private channel.
Do not accept an actor-supplied launch identifier or service authentication result as ownership evidence.
Keep the supervisor key outside service processes and workspace execution boundaries.

The issuer verifies supervisor proof and the exact activation context.
It does not infer kernel ownership from a caller's protobuf fields.
The production launch coordinator must supply that ownership guarantee before integration.
The issuer protocol alone does not complete supervisor recovery or safe replacement.

Additive protobuf interface

SignaturePurpose adds AUTHORITY_LAUNCH_AUTHORIZATION = 6.
Existing signature purposes and message fields remain unchanged.

AuthorityLaunchBegin contains:
1. AuthorityAuthenticationResult service.
2. uint64 supervision_revision.
3. bytes launch_id.
4. optional uint64 previous_generation.

AuthorityLaunchChallenge contains:
1. uint32 protocol_version.
2. bytes issuer_id.
3. bytes issuer_incarnation.
4. bytes nonce.
5. bytes connection_binding for the supervisor TLS connection.
6. AuthorityLaunchBegin request.
7. bytes supervisor_public_key.
8. uint32 lifetime_ms.
9. string audience, exactly identityd/authority-launch/v1.

AuthorityLaunchComplete contains nonce field1 and KeyProof proof field2.
AuthorityLaunchAuthorization contains request field1, authorization_id field2, generation field3, and supervisor_public_key field4.
Generation zero means authorized but not consumed. A positive generation records the consuming activation.
IssuerRequest adds authority_launch_begin field28 and authority_launch_complete field29.
IssuerReply adds authority_launch_authorization field27.
The begin operation returns the existing ChallengeReply envelope.

Validation

Identifiers, raw public keys, process incarnations, and connection bindings contain 32 bytes.
Registration and supervision revisions must be positive signed-64-bit values.
previous_generation must be present and fit signed-64-bit storage.
It must equal the participant's current last generation when a new authorization commits.
The service registration must exactly match the durable participant and its domains.
The service issuer identity and incarnation must match this issuer process.
The service security revision cannot exceed the current issuer revision.
The supervisor revision and key must match the current owner-controlled binding.

Both protocol operations require server-created TLS connection context.
The fresh challenge binds the full request and supervisor connection.
Use the existing bounded challenge pool and lifetime limits.
Consume the nonce before checking the supplied proof.
Reject another connection, key, signing purpose, changed request, expired challenge, and nonce replay.
Recheck durable registration, supervisor binding, and generation state after proof verification.
Owner, actor, and service signatures do not substitute for supervisor proof.

Persistence and activation

Explicit issuer schema8 migration adds authority_launch_authorization.
Store the exact request, supervisor key, authorization identity, and consumed generation.
Enforce unique authorization identity, launch identity, and participant/service-incarnation pair.
Migration creates no permission for an existing process or generation.
Keep schema7 bindings and all older state unchanged.
Use disposable databases for migration testing.

A new authorization cannot bypass an active generation.
A fresh valid proof may retrieve an identical committed authorization after a lost reply.
That retry returns the existing authorization identity and consumed generation without repeating activation.
Reject reuse of a launch or service incarnation with changed context.

Activation of a bound participant requires an unconsumed matching authorization.
Compare the entire server-derived service authentication result with the approved target.
Recheck supervisor key and revision before activation.
Recheck previous_generation and the current synchronized security revision.
Insert the new generation and consume its authorization in one transaction.
Rollback must preserve both records if either write fails.
Another connection using the same service key or incarnation cannot consume this authorization.
Starting one generation invalidates other approvals for its previous_generation.
Existing unsupervised behavior remains unchanged until an owner binds the participant.

Checked client and evidence

The production client remembers and validates the launch challenge context.
It consumes pending context before sending completion, including requests that receive typed denial.
It verifies the supervisor proof and exact returned authorization context.
Reject unsolicited success, changed requests, invalid generations, malformed fields, and contradictory keys.
No transparent retry may repeat an uncertain mutation.

Test real issuer activation, service-connection substitution, stale generations, key rotation, replay, and concurrent requests.
Test issuer restart, storage failure, unchanged revocation obligations, and explicit migration rollback.
Use independent TLS fault peers to test client reply validation.
Qualify both hosts in Debug and runtime ASan/UBSan before integration.

Fencing, checked external cleanup, durable reconciliation, and retirement remain subsequent requirements.
