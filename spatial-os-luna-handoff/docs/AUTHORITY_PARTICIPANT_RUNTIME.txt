Runtime participation and cancellation completion
Status: required runtime integration. A real world diagnostic reproduces missing participation.
Dependency: identity.participant_barrier candidate04. Keep all active qualification sources frozen.

Observed gap
A real TLS actor starts moving in the current world runtime.
The new issuer commits its revocation and reports a complete barrier with zero participants.
The diagnostic relay holds the genuine revocation event while the actor continues moving.
The world never registered or activated an authority participant, so the issuer cannot include it.
Delivery then stops motion. The issuer's empty obligation set does not establish runtime cancellation.
This is missing runtime integration, not a passed Spatial-M1 requirement.
See evidence/revocation-barrier-2026-10-09/runtime-participation-gap-01/sb16.

Required invariant
Every world or broker that admits protected activity has an active, registered service generation.
It acknowledges a revision only after its actual cancellation effects and affected handler stack are settled.

Reusable transport component
Add src/identity/participant_runtime.hpp and participant_runtime.cpp.
ParticipantRuntime owns its checked issuer TLS client on one worker thread.
Main-thread poll never waits for network I/O.
Only activate, applied, and release commands enter its bounded command queue.
Use existing checked IssuerClient operations. Do not create a second authorization implementation.
Generate a fresh process incarnation inside the runtime.
Load the registered service key from an owned private file outside workspace mounts.
Verify the returned registration matches the configured identity, revision, key, and exact expected authority domains.
The world derives expected domains from its stable world identity.
The broker derives expected domains from every configured workspace authority binding.
Do not infer domains from host names or actor identities.

Worker lifecycle
Authenticate the service on the actual TLS connection.
Publish a checked revocation baseline before activation.
Continue polling contiguous events while the authority synchronizes.
A matching baseline is observed state. It is not permission to admit protected work.
The authority explicitly requests activation after synchronization and cleanup.
A concurrent revocation can reject activation with REVISION_CONFLICT.
Publish that rejection and new feed events. Require a new explicit synchronized activation request.
Never automatically retry an uncertain mutation.
Publish activated only after the issuer confirms the durable generation.
Keep feed and mutation traffic on that original service connection.
Bound idle feed waits so queued acknowledgements and stop requests make progress.
Do not advance applied state merely because a feed batch advertises a newer head.
Require queued application revisions to be contiguous and no newer than events delivered to the consumer.
Bound both update and command queues. Overflow permanently disables the channel and reports uncertainty.
A transport failure permanently disables that instance. Do not silently reconnect or replace its generation.
Clean release requires the authority's explicit quiescence confirmation.
Destroying the worker stops I/O without claiming release or deleting issuer obligations.

Recovery
A disconnected or crashed generation remains unresolved at the issuer.
A second process with the same service key cannot replace it.
Add a separately reviewed trusted-supervisor fencing and cleanup path before recovery acceptance.
Require verified native input, process, lease, and observation cleanup before resolving a stranded generation.
An owner assertion, elapsed timeout, lost socket, or process exit alone is insufficient.
Do not clear unknown external effects to obtain a successful barrier.
