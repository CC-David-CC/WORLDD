M07 copy journal schema v5
Date: 2026-10-14

ExecutionStore remains the single authority for its existing SQLite database. Schema v5 adds private `copy_operations` and `copy_effects` tables. It does not make SQLite atomic with storage, filesystem, process, or Git effects. The database continues to use its existing exclusive execution lock and transaction settings.

Fresh execution databases create schema v5. Existing schema v1, v2, and v3 databases use their existing explicit migration options and complete at v5. This changes their observable `user_version` result from 4 to 5; their existing explicit migration tests now assert v5 and normal reopen. Tests that synthesize an old v1, v2, or v3 database from a current database drop the v5 copy tables before lowering `user_version`, so each fixture represents its declared historical schema. The v1/v2/v3/v4 migration flag remains rejected when combined with the fixture-fault option. Repeating the matching explicit migration after reaching v5 succeeds without changing records. Existing schema v4 databases remain refused by ordinary startup. Operators must stop the broker and run `workspaced --state-dir PATH --migrate-v4`. All v1-to-v5, v2-to-v5, v3-to-v5, and v4-to-v5 upgrades run in one SQLite transaction; a failed step rolls back the original version and all schema/data changes. The migration is transactional, preserves all existing rows, sets `user_version=5`, and exits before serving. A failed migration rolls back the new tables and version change. Reopen normally after success. The existing default refusal for old schemas remains in place.

`copy_operations` binds the 16-byte operation ID to the authenticated requester, exact serialized request, SHA-256 request digest, source workspace, pinned authority and policy revisions, destination profile and profile revision, requested data classes, phase, error, destination identity, private manifest bytes and digest, and the exact transition payload. Reuse with changed request bytes or requester conflicts. These private rows and receipts must never be copied into actor-facing status replies.

`copy_effects` records one exact external-effect intent per operation/effect ID before the effect starts, then stores its typed receipt after the effect is proven. Exact retries are idempotent. Reused effect IDs with changed intent or receipt bytes conflict. Restart leaves an operation in its last durable phase when no effect is unresolved. An unresolved effect intent moves a nonterminal operation to `UNCERTAIN`; the journal does not infer that an external effect succeeded. `PUBLISHED` requires a validated destination identity and private manifest digest. Generic phase transitions cannot enter `VALIDATED` or `ABORTED`; those states require proof-bearing journal APIs. Publication intents bind every exact destination object identity and its separate StorageOwner operation digest.

Phase advancement is monotonic. `PUBLISHED`, `ABORTED`, and `UNCERTAIN` are terminal. Same-phase retries require byte-identical transition payloads. A manifest is bounded to the 1 MiB transport ceiling, an operator-provided entry and byte limit, registered typed storage identities, unique class/object pairs, one supported version-1 schema identifier per data class (`spatial.workspace.project-tree`, `spatial.workspace.git-history`, `spatial.workspace.application-definition`, `spatial.workspace.application-state`, or `spatial.workspace.environment-config`), a project/Git-history pair, and one matching read-only snapshot receipt per entry. Caller-provided paths are not accepted.

Requester bindings are exact opaque 64-byte issuer-key plus actor-key identities. The journal stores them as BLOBs and accepts NUL and non-UTF-8 bytes; labels are rejected.

The journal uses configurable internal admission limits. Defaults retain at most 4,096 operation records and 64 effect intents per operation. Hard configuration ceilings are 65,536 operations and 256 effects per operation. Conditional insert statements enforce admission atomically before any caller performs an external effect. Capacity failures carry the typed `COPY_EXHAUSTED` result for caller mapping. Exact operation retries, admitted effect receipts, and recovery remain available at capacity. The journal never deletes terminal history to reclaim space. These are implementation defaults, not a new public quota or a change to storage-owner limits.

The journal API returns the exact bound request only after requester, canonical protobuf, operation-ID, and digest checks. Validation stores the exact framed snapshot receipt set with the manifest and compares it byte-for-byte on retry. Manifest classes must equal the request classes, the destination workspace must be new, and publication receipts cannot reuse source or snapshot IDs or subvolumes. Effect retrieval validates row lengths and receipt-state consistency before exposing private records. Invalid numeric data-class values are rejected before conversion to the generated enum type.

The focused journal and migration tests cover request idempotency and conflicts, configured operation/effect capacity with retry and completion at capacity, phase transition conflicts, terminal immutability, effect intent and receipt retries, unresolved-effect recovery, manifest limits and duplicate entries, old-row preservation, default v4 refusal, explicit migration, normal reopen, and migration rollback. These checks do not implement or qualify the complete workspace copy pipeline. Runtime qualification remains pending review and deployment.
