Scope and trust path

The journal now has a strict lookup for a saved scope-cleanup disposition. It
requires the caller's exact durable job row, the current pinned execution and
journal binding, and the workspace-to-worktree binding. It compares the current
job bytes, immutable normalized job digest, workspace, worktree, job ID, and
saved broker-root device, inode, boot ID, and launch-ID shape. If a durable
parent generation exists, its root tuple, parent identity bytes, normalized
absolute path, and root name must match. A serialized outcome or path alone
cannot authorize recovery.

The Store pins the already initialized execution state through the planned
ExecutionStore canonical directory-FD accessor, then retains the pin for its
lifetime. It does not open another ordinary SQLite descriptor. The journal
lookup uses the existing managed journal connection; the pinned VFS validates
its own retained inode set. The implementation still needs integration with
the deadline worker's per-open managed-connection deadline context before it
can satisfy the inherited cleanup deadline on busy SQLite operations.

Before recovery constructs a FileEngine, Store validates each recovery job's
saved disposition. Conflict kinds quarantine that worktree, so copy poll and
START replay cannot return cached receipts. FileEngine checks the same
validated disposition before cancellation, prior-proof bypass, publication,
or stage cleanup. Missing, replaced, invalid-parent, and immutable-uncertainty
outcomes retain the job's old proof, terminal uncertainty bytes, stage bytes,
and parent evidence. The Store's quarantine set prevents later file actions.

A valid RESERVED_SCOPE_RECONCILED disposition is accepted only for the exact
START_INTENT job with neither worker identity nor drain proof. It may reconcile
when its old parent record has already been pruned. It skips a second attempt to
remove that reservation. It creates no worker proof. Jobs with no disposition
still require the existing exact worker proof or a successful exact native
stop before recovery can proceed.

Pruning selects only eligible terminal rows (states 4, 5, 6, and 8) in a
bounded batch. For each selected job, it deletes the paired disposition and
job row in the same transaction. UNCERTAIN (state 7), active jobs, and all
unselected evidence remain. The outcome table's existing row cap and
idempotent insertion policy remain in force.
