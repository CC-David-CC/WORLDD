# M08 storage contention repair checkpoint

Status: UNQUALIFIED. Runtime and build checks are UNRUN. Primary review rejected this draft; do not integrate it.

## Finding

The paired retained diagnostic shows that revocation delivery and reconciliation reach the broker quickly. The reproduced sb16 failure had all five processes belonging to the held application exit, while four writer-scope processes remained alive at the existing two-second sample. Those four were bwrap, namespace leader, app-init, and Python writer; only Python was in the payload cgroup.

The broker thread then observed fdatasync on a directory descriptor whose target was the fixture volume directory. A writer process also remained in Btrfs wait_log_commit. This does not identify the sync as SQLite database persistence. The paired sb16-2 run passed the same barrier. See external pair audit SHA 9b03705b7774faebc29259470706114ee389444f759c9758cf5433c30d656d94.

The repair therefore addresses a proven ordering defect: the old loop erased each revoked application and synchronously waited before requesting stop for the next application. Writer activity could continue while an earlier application drained. The patch requests stop for every known revoked application before any per-application wait, then drains all using one deadline fixed at the first batch request. It does not claim to cure a long kernel sync or native cleanup latency.

## Changes

ApplicationProcess now exposes owner-thread request and completion phases. Existing stop() still composes them for other callers. The first deadline is retained across retries. Request failures are remembered while all owned stop mechanisms are attempted. Completion is attempted for every process even after another completion fails.

Authority reconciliation collects valid revoked rows, sends stop requests to every associated in-memory job, then completes all jobs on the broker owner thread. It preserves the existing no-job row behavior for startup/recovery windows. Native credential cleanup and the existing file-copy cancellation run after all app drains, so neither delays the shared app stop deadline. One transaction updates all revoked rows and verifies every expected row transition. Reconciliation failures remain latched on the owner thread. Every later main-loop enforce call checks that latch before settlement or dispatch work, so a caught request error cannot lead to a later applied-revision acknowledgement.

A process termination regression was added for repeated stop requests with an existing cgroup permission fault. It checks that retries do not reset the original two-second deadline. The new tests were not executed. Primary review found that the issuer-barrier regression does not force a Git/filesystem observer inside request dispatch and can observe the pre-work pending state, so it does not prove that no later acknowledgement occurs.

Primary review also found a copy-only regression: the early return when no application rows are revoked skips the moved file-copy reconciliation block. A workspace with active copy jobs and no running/revoked applications would not cancel those jobs. Preserve file_action_dispatch_active and pending-reconcile semantics while correcting the ordering.

## Limits and review points

The fdatasync target remains unattributed; do not label it a database file. Synchronous scope drain, native credential revocation, and SQLite commit may still exceed the existing acknowledgement or process-exit bounds. A second asynchronous ownership design may be needed if focused runtime evidence demonstrates this.

Malformed or unreadable running rows cannot safely be classified as revoked. They must keep reconciliation failed and prevent acknowledgement. Valid rows already observed should still receive cancellation and drain attempts. A missing in-memory job retains existing durable-row handling; no new invariant is imposed.\n
