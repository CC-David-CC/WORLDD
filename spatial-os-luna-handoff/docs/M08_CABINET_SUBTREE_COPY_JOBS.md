# M08 cabinet subtree copy jobs

Status: contract change from the M08 typed-UNIMPLEMENTED placeholder. Public protobuf field numbers remain unchanged. This contract changes only `FileCopyJob` semantics. This branch implements the confined worker and an unqualified FileEngine START/POLL/CANCEL lifecycle. The combined candidate includes a version 7 journal and restart reconciliation with durable exact-scope drain acknowledgments. Runtime qualification remains pending. The branch is not qualified.

## Requests and ownership

`START` requires an empty `job_id`, valid source and destination-directory handles, a valid basename, positive byte and entry ceilings, and a fresh `FILE_COPY` grant. The server creates a random 16-byte job ID. The initiating principal owns that job. A journal drain acknowledgment binds the exact stored ProcessScope identity; workers cannot issue that acknowledgment. Every poll and cancellation requires the same principal and a fresh `FILE_COPY` grant. The broker authority watcher also rechecks active jobs when it consumes an authority change. It stops jobs whose owner lost `FILE_COPY` without waiting for another client request. Workspace selection or cabinet presentation alone does not grant copy authority.

A source handle may identify one regular file or one directory subtree. A file copy counts the root file as one entry. A directory copy counts the root directory and every descendant. Only regular-file payload bytes count against the byte ceiling. The destination must not exist. The destination may share a parent with the source, but it may not lie within the copied directory subtree. Invalid or stale handles, symlinks, nested mounts, hard links, special files, and source changes fail closed.

The copy preserves regular permission bits masked to `0777`. It copies no ownership, xattrs, ACLs, credentials, host paths, or special files. Production staging uses a broker-private sibling directory named `.spatial-copy-staging-<worktree-id>` beside the managed project directory. Each job has a random `.spatial-copy-stage-<job-id>` child. Application namespaces bind only the granted project directory at `/project`; the sibling is outside that mount. Broker and worker retain pinned staging descriptors. They validate filesystem and subvolume compatibility before atomic no-replace publication. The old in-project `.spatial-copy-staging` name remains reserved and masked for legacy fixtures. That legacy mask is not the production sibling's authority boundary. The existing adversarial mask test exercises the legacy mount order. Production sibling confinement requires its resource-backed qualification.


A worker rejection before publication returns a terminal `FAILED` receipt with typed `failure_code` only after the ProcessScope is proven empty and identity-checked staging cleanup is synchronized. This is an additive FileCopyJob protocol state; it does not change existing field numbers or states. If either proof fails, the job remains `UNCERTAIN`.

The client ceilings must be positive and no larger than the server ceilings: 4 GiB of payload bytes and 200,000 entries. The worker enforces both limits during enumeration and copying. It also enforces maximum nesting depth 128 and a descriptor budget derived from its actual `RLIMIT_NOFILE`, reserving 16 descriptors and charging three descriptors per nested level. Initialization reconciles journaled stages first. Recognized UNCERTAIN stages stay untouched. Unrecognized entries still fail closed. The broker admits at most 16 active cabinet copy jobs per workspaced instance. Each job uses the existing `WorkspaceResources` worker cgroup budget. The project filesystem quota remains the storage limit. These ceilings do not change M07 workspace-copy limits or behavior.

## Worker and digest

The helper runs inside the existing no-network copy sandbox and `ProcessScope`. The source is read-only. Staging is writable. The helper receives only pinned descriptors and a sealed, bounded protobuf request. Authority, the journal, job lifecycle, cancellation, and publication remain in the broker process.

Content digest is SHA-256 over this canonical byte stream. All integer lengths and counts use unsigned 64-bit big-endian encoding. Byte strings are encoded as length followed by raw bytes. The stream begins with the length-prefixed domain string `spatial-cabinet-copy-v1`. It then encodes the source root as an entry with an empty relative path, type byte `F` or `D`, and permission bits masked to `0777`. Directories are enumerated in lexicographic unsigned-byte name order. Each descendant contributes its length-prefixed relative path, type byte, and masked permission bits. A regular file then contributes its 64-bit payload length and exact payload bytes. A directory contributes its descendants. Synchronization is a required precondition for a successful receipt and is not hashed. No timestamps, inode numbers, or host paths enter the digest.

Before publication, the worker verifies that each opened file retains its pinned device and inode, link count, size, mode, modification time, and change time. It verifies directory identity and metadata after enumerating descendants. It synchronizes every copied file and directory and the staging parent. The broker rechecks fresh authority and the destination parent identity before atomic no-replace publication.

`POLL` returns only bounded monotonic progress and a terminal receipt. Progress counts include entries observed and bytes copied, never exceed the request ceilings, and are journaled. `COMPLETE` is returned only after publication identity and digest are durable. A pre-existing destination is never changed. A conflict removes only staging whose recorded identity still matches the job.

A worker rejection before publication returns `FAILED` only after the same stop, cleanup, and synchronization proofs. The receipt reports a typed `failure_code`. A failed proof returns `UNCERTAIN`. `CANCEL` returns `CANCELLED` only after the owned ProcessScope is proven empty, staging cleanup is identity-checked and synchronized, and the terminal journal commit succeeds. A denied `POLL` or `CANCEL` for the matching job owner stops the worker and removes staging before the broker returns `UNAUTHORIZED`. Separately, authority reconciliation cancels an active job after the broker consumes a change and confirms that its owner lost `FILE_COPY`; no follow-up poll or cancellation is required. If worker stop or stage cleanup cannot be proven, the job becomes `UNCERTAIN`. A foreign principal cannot stop another owner’s job. The copy worker cannot publish by itself; publication occurs only during an authorized broker poll. If stop or cleanup cannot be proven, the job stays `UNCERTAIN`. If a filesystem effect may have happened, or journal completion cannot be proven, the job becomes `UNCERTAIN` with its job ID. The application process remains alive.

## Durable identity and recovery

The file-operation journal binds each actor request to workspace, operation ID, principal, worktree root identity, exact right, canonical request digest, and engine incarnation. A versioned journal extension stores copy job ID, initiating request and principal, server-approved limits, source identity and relative path, destination-parent identity, basename, staging identity, ProcessScope identity, boot ID, state, progress, and terminal receipt. SQLite remains confined to its existing journal owner thread. Journal limits and fail-closed behavior remain in force.

On restart, recovery never relaunches a worker. If the recorded boot ID differs from the current kernel boot ID, the old worker cannot still exist. For a same-boot restart, recovery may clean staging only if the exact recorded ProcessScope can be reopened by its delegated-root-relative identity, its device and inode match, and `cgroup.events`, `cgroup.procs`, and descendants prove it empty. Without an exact durable drain acknowledgment, failure to reopen and prove the scope empty preserves staging and records `UNCERTAIN`. Recovery does not claim cancellation, remove staging, or commit `COMPLETE` from scope absence. A missing or replaced scope cannot itself prove emptiness. The broker may instead use a previously durable acknowledgment for the exact recorded scope identity. That acknowledgment is written after verified stop and before scope removal, staging cleanup, or publication. It cannot be removed or rebound. Prior-boot drainage remains a separate kernel-boot proof.

Recovery first checks whether the exact published destination matches its durable device, inode, type, limits, count, and digest receipt. If the exact destination receipt is proven, recovery may commit `COMPLETE`; publication itself is allowed only after the worker scope is confirmed empty. Otherwise, recovery removes staging only when the ProcessScope is proven empty and the recorded staging device and inode still match; it then synchronizes the parent and commits `CANCELLED`. If same-boot scope emptiness cannot be proven, it preserves staging and commits `UNCERTAIN`. Any other unprovable identity, authority, cleanup, or journal result also stays `UNCERTAIN`. Recovery never repeats publication or removes an unrelated object.
