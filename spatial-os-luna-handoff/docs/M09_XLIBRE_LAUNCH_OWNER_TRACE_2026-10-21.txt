Finding
-------
In the inspected pinned component source, no production XLibre server launch owner is established.
It contains a production host-session owner for the compositor process, spatialwm.
That process connects to a separately identified X server. HostSessionConfig has no X server executable, arguments, privilege profile, or observer-arm descriptor field.
No production caller or configuration builder for the host-session executable was found in this pinned component source tree.
This source search does not establish whether external deployment configuration provides a launcher.
The identity of the real parent that constructs HostSessionConfig is therefore unresolved.

Production host-session chain
-----------------------------
1. src/supervisor/host_session_main.cpp:166-182 parses CONFIG_FD, CONTROL_FD, and parent PID, checks the peer, parses the trusted config FD, and validates inherited descriptor aliases.
   HostSessionConfig is documented as trusted parent input in proto/spatial/supervisor/v1/host_session.proto:9-23.
   It names supervisor_executable, compositor_executable, compositor state, and sealed broker/compositor config FDs. It does not name an X server.
2. host_session_main.cpp:185-205 constructs SessionCoordinator, starts presentation with compositor_executable, then starts configured worlds and the actor controller.
   World supervisor launches are separate: session_coordinator.cpp:249-257 constructs SessionLaunch for each world executable and AuthoritySupervisorConfig.
3. session_coordinator.cpp:103-110 implements start_presentation by constructing PresentationOwner from the configured executable, state path, and borrowed compositor-native FD.
4. src/platform/presentation_owner.cpp:24-32 consumes the sealed compositor config and constructs RenderProcess with its display and descriptor.
   compositor_native.proto:4-12 identifies that message as NativeCompositorConfig. It carries display number, compositor cookie, server ID, server PID, and server UID.
   This is compositor authentication data. It is not observer-arm input.
5. src/platform/render_process.cpp:15-58 forks and execs the configured presentation executable. Its Presentation mode passes --state-dir, --display, --native-security-fd, and --presentation-owner-pid.
   It closes unrelated descriptors, clears CLOEXEC only on the compositor config FD, and opens a pidfd for the child.
   The forked child begins with the host-session credentials. This code performs no explicit UID/GID transition. Final credentials could still depend on executable metadata, which this source path does not verify.
   src/platform/render_process.cpp:66-76 waits for child exit, kills on timeout, reaps, and closes the pidfd.
6. tests/native/test_host_session_production.py:165-175 supplies spatialwm as compositor_executable in a fixture. This confirms the intended executable role, not a production X server launch.

SessionLaunch is not the missing X server owner. Its constructor accepts AuthoritySupervisorConfig and launches the configured authority supervisor with a sealed native config, management socket, and optional ChildHandleServer channel (src/supervisor/session_launch.cpp:145-208). It does not launch Xorg or spatialwm. Its inherited_source_fds belong to that supervisor launch. Reusing them would pass authority to the wrong process boundary.

Bounded proposal for primary review
-----------------------------------
Do not add the arm handoff to SessionLaunch, AuthoritySupervisorConfig, ChildHandleServer, CompositorConfig, or the X-client authorization callback. Those boundaries do not own the X server process.
First identify and approve the actual production X server launcher and its privilege transition. The source currently does not name one. The next safe investigation is to trace the native-session entry command/configuration that should create Xorg, then confirm its executable, UID/GID, startup handshake, pidfd/process identity, and teardown owner from source and the accepted runtime configuration.

Once that owner is established, the smallest bridge should add one private inherited endpoint only to that X server child. Keep CLOEXEC on all descriptors by default. Clear it only for the verified X server child. Close the parent's child-end copy after exec confirmation and close the child input after one consume or rejection. Do not let the compositor receive it.

Use a single bounded NativeInputObservationRecordV2 with protocol_version 2 and exactly one Arm payload, unless primary review approves a different envelope. The server must validate complete parsing, size limits, session and arm IDs, monotonic arm/deadline ordering, deadline freshness, expected role and identities, and one-shot consumption before capture. It must independently resolve live native pins; arm fields cannot substitute for that check. Reject repeats, truncation, extra frames, EOF before one valid arm, stale launches, wrong child identity, and timeouts. Keep worldd seat binding on its separate private endpoint. Keep ProbeReceiptBatch independently produced.

Required focused regressions after an owner is approved: only the verified X server child inherits the endpoint; compositor and sibling children do not. Check FD flags, /proc child ownership, one complete arm, replay, duplicate descriptors, stale launch/session, malformed and oversized frames, early EOF, timeout, and closure on success, rejection, and child exit. Assert no capture or success output before arm validation and live-pin resolution. Retain existing parser, collector, and serializer checks. Later native acceptance must independently prove the production owner, descriptor handoff, XACE server identity, worldd binding, and physical-input lifecycle.

Separate future work
--------------------
The worldd seat-binding endpoint and its trusted producer remain separate from Xserver arm input. The independent ProbeReceiptBatch producer also remains separate. Neither is implemented or proven by this trace.
